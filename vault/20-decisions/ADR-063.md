## Context

Phase 8 needs a durable queue: something Pinot consumes from, and something the
Parquet/Iceberg files are formed from. PRD §6.2 already fixed half of it — the
target is a "Kafka-compatible durable event backbone", and §7 adds that
"Redpanda may be used as a Kafka-compatible deployment choice when operationally
preferable". §6.3 says the interfaces are built so `EventPublisher`/
`EventConsumer` have in-process and Kafka implementations.

So the protocol is decided. What is not decided is **which broker** and, more
importantly, **what turns the stream into Iceberg tables.** Three candidates,
checked against their own documentation rather than recalled:

**Redpanda Iceberg Topics.** Redpanda can materialise a topic directly as an
Iceberg table — Parquet in object storage, no ETL. It requires Tiered Storage,
and both Tiered Storage and the Iceberg integration are **enterprise-licensed**.

**The Apache Iceberg Kafka Connect sink.** Official, Apache-2.0, fans out to
multiple tables. Its catalog support is REST, Hive, Glue, Nessie and BigQuery
Metastore. Ours is `pyiceberg`'s SQL catalog ([[ADR-060]], verified against the
stack's PostgreSQL in [[REQ-WP-041]]), and the only catalog both a Java
connector and `pyiceberg` can share is REST. Adopting the sink therefore means
replacing the catalog with a REST service.

**A consumer in this repository**, appending through `IcebergTable`.

## Decision

**The broker is Redpanda on the dev stack, and the code stays Kafka-protocol.**

**The Parquet is written by our own consumer, not by a connector or by the
broker.**

## Why not the connector or the broker's own integration

Iceberg Topics costs an enterprise licence on the core data path, for a project
that has not needed one anywhere else. That alone would not settle it. This
does:

**Both alternatives write our tables while knowing none of our rules.**
`IcebergTable` is not a thin wrapper. It refuses an empty append, because a
snapshot saying something happened when it did not is believed downstream. It
computes [[ADR-053]]'s content hash over rows, which is what PRD §0 item 13's
reproducibility rests on. It reconstructs commit order from sequence numbers,
because the scan returns the newest first and every "latest row wins" reader
folds in order. And [[ADR-056]] requires every pipeline entry point to read a
per-series watermark before writing — a rule that exists because duplicate
writes on re-run were a real defect in this repository, found and fixed.

A sink connector honours none of that. It would produce Iceberg tables that look
identical and carry none of the guarantees, and the first symptom would be a
replay writing the same bars twice.

The rule the connector would break is the one written down precisely so that a
future writer could not break it by accident. Adopting a writer that cannot read
our rules is not integration; it is a second ingestion path.

## Why Redpanda, and why the choice is cheap

Single binary, no JVM and no ZooKeeper, which matters for a dev stack that
already asks for PostgreSQL and MinIO. The Community Edition is BSL, converting
to Apache 2.0 four years after each merge; self-hosted production is permitted
and reselling it as a service is not, which is not something this project does.

**The choice is reversible by construction.** Redpanda speaks the Kafka
protocol, so moving to Apache Kafka changes a compose file and a bootstrap
address, not a line of application code. That is the only reason it is safe to
decide now rather than later: a decision that costs a compose file to reverse
does not need to be right the first time.

## Consequences

Two consumers of one log: Pinot for HOT serving, and ours for the canonical
plane. That is the fan-out PRD §6.4's diagram shows, and it keeps the two
answerable separately — Pinot can be absent, as [[ADR-002]] deferred it, without
the canonical path noticing.

The cost is that the Iceberg writer is ours to maintain, including batching and
the watermark discipline. That cost is the point: it is where the guarantees
live.

**Unverified and marked as such**: how Pinot's real-time tables consume a topic
in detail. The documentation pages read for this decision were introductory, and
Pinot is deferred by [[ADR-002]] anyway. Nothing here depends on it beyond the
topic being Kafka-protocol, which is the whole reason to standardise on the
protocol rather than on a product.
