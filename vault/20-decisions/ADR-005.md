## Context

REQ-WP-005 requires a "late-event policy". PRD §12 specifies what a bar
contains and that signals use only finalized bars, but it never says what
happens to a trade that arrives carrying an `event_time` inside a window that
has already closed. Searching the PRD for the term finds only the requirement's
own bullet.

Something must be decided, because the situation is routine rather than
exceptional: exchange websockets deliver out of order, reconnections replay, and
backfills overlap live data.

## Decision

**A bar, once finalized, is never amended.** A trade whose `event_time` falls in
a finalized window is discarded, and a counter for late trades increases.

**A bar finalizes when the watermark passes its window end plus a grace period.**
The watermark is the highest `event_time` observed so far — never wall-clock
time. The grace period is configuration, defaulting to five seconds.

**A trade arriving during the grace period is accumulated normally**, even
though its window has ended. The window is closed to new time, not to late
arrivals, until the grace expires.

## Consequences

- **Reopening a bar was never an option.** PRD §0.5 forbids rewriting finalized
  snapshots, and a bar amended after close is exactly that. Silently amending
  would also mean a feature computed at time `t` could change afterwards, which
  §0.3 forbids and which is the definition of repainting this project exists to
  prevent.
- **The grace period is where the real trade-off lives.** Too short and ordinary
  out-of-order delivery is discarded; too long and every bar is stale before it
  can be used. Five seconds is a starting default, not a finding — PRD §0.12
  requires thresholds to be configurable, and this one will need measuring
  against real venue behaviour.
- **Dropped trades are counted, not swallowed.** A late-trade counter makes the
  grace period measurable: if it climbs, the window is too short, and the
  operator can see that rather than infer it from missing volume.
- **The watermark is event-time, never wall-clock.** Using local time to close a
  bar would make bar boundaries depend on our own latency, so a replay and a
  live run would produce different bars from identical input — breaking
  Principle VII, which is the property the whole backtest rests on.
- **A quiet market leaves the last bar open indefinitely.** That follows from an
  event-time watermark and is correct: with no trades, there is no evidence the
  window has passed. A consumer needing a periodic heartbeat must supply one as
  an explicit event rather than have the builder invent time.
- Reversible: widening the grace or adding a wall-clock fallback are both
  configuration-shaped changes. Amending finalized bars is not reversible, which
  is why that door stays shut.
