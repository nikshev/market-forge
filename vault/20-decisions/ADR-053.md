title: A dataset's identity is a hash of its rows, not of its files

## Context

PRD §29.B ends its list of canonical tables with a sentence that is easy to read
past: "Every research-grade table must support dataset lineage/snapshot
reproducibility." PRD §0 item 13 says what that is for — a result must be
reproducible from "a versioned dataset + config + code commit hash + model
artifact hash". The dataset needs a version, and the obvious version of a set of
files is a digest of their bytes.

That obvious answer is wrong here, and the reason is measurable rather than
theoretical. Parquet writes a `created_by` string into every file's footer. On
the machine this was built, `pq.write_table` produces
`parquet-cpp-arrow version 25.0.1` in a 721-byte file for three rows; a
`pyarrow` upgrade changes that string and therefore every byte-digest in the
lakehouse. Compression settings do the same: the default and `zstd` produce
different files for identical data.

A dataset identity with that property fails at exactly the moment it matters. A
research run recorded in September stops matching its own dataset in October
because a dependency moved, and nothing about the data changed. Every
comparison keyed by dataset — [[REQ-EXP-015]]'s "same walk-forward folds",
[[REQ-EXP-017]]'s "exact same immutable entry signals" — would start reporting
differences that are library releases.

## Decision

**A snapshot's `content_hash` is computed over its logical content**: the schema
fingerprint, and the per-file digests of the rows in the schema's own canonical
encoding. No Parquet byte ever enters it.

The encoding is length-prefixed and type-tagged. Length prefixes because a
separator can be forged by a value containing it, and `("ab", "c")` and
`("a", "bc")` sharing an identity is exactly the kind of collision nobody looks
for. Type tags because Python's `1`, `True` and `"1"` would otherwise have to be
told apart by their bytes, and two of those three are identical.

**Each file also carries a `file_sha256` over its stored bytes**, and it answers
a different question: whether this object is the one that was written. It is
integrity, not identity, and the two are kept in separate fields so nothing has
to guess which is meant.

**The digests are per file and combined by sorting**, so appending a file does
not require rehashing the ones already committed, and a manifest that lists its
files in a different order still names the same dataset.

## Consequences

- **A dataset written twice, anywhere, has one name.** Two stores, two
  processes, two library versions: same rows, same identity. That is the
  property PRD §0 item 13 needs and the byte digest cannot give.
- **Hashing costs a pass over the rows at write time.** Accepted: it is linear,
  it happens once per file, and the alternative is an identity that does not
  identify.
- **`-0.0` and `0.0` are different content.** They compare equal and are
  distinct bit patterns that Parquet stores distinctly; a hash calling them the
  same would let a file change without its identity changing.
- **A manifest records its own content hash as well as its files**, so an edit
  that changes one without the other is caught on the next read rather than
  believed.
- **This is not the Iceberg specification.** Iceberg's own manifests carry file
  paths and statistics, and its identity is the snapshot id in a catalog. What
  §29.B asks for is the property, and this is the property; adopting the full
  specification later means writing a compatible manifest, not changing what a
  dataset means.
- **Reversible in one direction only.** Identities computed this way survive a
  library upgrade; identities computed from bytes would not, so switching to
  byte digests later would silently rename every dataset in the lakehouse.
