## Context

PRD §17.2 lists lead-lag features and then forbids the obvious next step: "Do
not convert correlation to trading rule without OOS validation."

The prohibition cannot be checked as written. There is no test for "nobody
converted this into a trading rule" — the conversion happens in someone's head
and lands as an ordinary-looking condition in a signal.

What can be checked is narrower and useful: that the signal path does not
import the module. A rule built on lead-lag has to reach the correlation
somehow, and in this codebase reaching it means importing it.

## Decision

**Lead-lag outputs declare themselves research-only**, carried on the value
rather than in documentation.

**A test asserts that no module under `signals`, `alerting` or `stops` imports
the lead-lag module.** The list is explicit: a test over "the signal path"
loosely defined would drift as packages are added.

## Consequences

- **The check is narrower than the prohibition, and says so.** Someone can
  still copy a correlation into a spreadsheet, decide a threshold and hard-code
  it. What they cannot do is wire it in and have the suite stay green.
- **The import list must be maintained.** A new package that makes trading
  decisions has to be added, and nothing enforces that — the same honest gap as
  `@pytest.mark.trace` markers, which also assert something no tool verifies.
- **Third use of this shape.** [[ADR-022]]'s transform declares whether it looks
  forward and the production path refuses the ones that do; [[ADR-027]]'s
  price/OI regime is a label nothing acts on. In each case an unverifiable
  prohibition became a verifiable structural fact.
- **OOS validation now exists**, in REQ-WP-017's purged folds and REQ-WP-018's
  comparison report. When someone wants a lead-lag rule, §17.2's condition is
  satisfiable rather than theoretical — and this ADR is what they will have to
  revisit rather than route around.
