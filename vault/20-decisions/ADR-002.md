## Context

PRD §7 defines two storage profiles. The **MVP profile** names ClickHouse as the
single-node time-series store "for fastest path to validating edge", alongside
PostgreSQL and object storage. The **target product profile** names Apache Pinot
for HOT serving, S3-compatible object storage as the canonical data plane,
Parquet as the physical format, Apache Iceberg for table semantics, Trino for
distributed research SQL, DuckDB for local and CI analytics, and PostgreSQL for
transactional metadata — with ClickHouse listed as "optional MVP/compatibility
backend, not mandatory at scale".

PRD §29.C supplies a ClickHouse mapping for the domain schemas, and §29.0 states
plainly that those schemas "are domain schemas, not a requirement that ClickHouse
is the final system of record", and that "any backend-specific DDL must live
behind migrations/adapters and must not leak into signal/channel domain code".

## Decision

**ClickHouse is not part of this project.** The target profile is adopted from the
start: Parquet on S3-compatible object storage with Iceberg table semantics as the
canonical data plane, DuckDB for local and CI analytics over extracts, PostgreSQL
for transactional metadata and control plane. Pinot is deferred until a HOT serving
requirement actually exists — it is not needed to validate edge.

The MVP profile is therefore skipped rather than passed through. PRD §29.C's
ClickHouse mapping is treated as reference material for the domain schemas it
describes, not as an implementation target.

For the local development stack this means **PostgreSQL and MinIO**, and no
analytical database service. MinIO rather than a plain local directory is a
judgement call: the target profile makes S3-compatible object storage the
canonical durable data plane, so developing against a filesystem and switching to
S3 later would reintroduce exactly the local-versus-production divergence that
Principle VII exists to prevent. DuckDB is a library, not a service, and needs no
container.

## Consequences

- One fewer service to run, and no migration from ClickHouse to Iceberg later.
- The domain schemas in PRD §29.1-29.8 stand unchanged; only their materialization
  differs. §29.0's adapter rule is what makes this substitution safe, and it must
  be honoured — backend specifics stay behind migrations and adapters.
- Research queries run through DuckDB locally rather than ClickHouse SQL. Trino
  arrives only when the data outgrows a single machine.
- This is a deliberate deviation from PRD §7's MVP profile. The PRD is read-only
  and still says what it says; this ADR is the record of why the implementation
  differs. `REQ-PHASE-0`'s requirement body quotes the PRD verbatim and therefore
  still lists "Postgres/ClickHouse connectivity" — that text is provenance, not an
  instruction, and its Notes section points here.
- Reversible at a cost: reinstating ClickHouse means a container, a driver, and a
  §29.C mapping. Nothing in this decision destroys that option.
