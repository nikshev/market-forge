title: A backup restores where it came from
status: accepted
decides: [REQ-WP-037, REQ-WP-039]

## Context

[[REQ-WP-037]] built a backup that does not care where it lands. Its keys are
relative — `cex_trades/data/00000001/….parquet` — so a restore can go into a
different bucket, a different endpoint, or a local directory, and three of its
tests turn on exactly that.

[[ADR-060]] moved the plane to Iceberg, and Iceberg writes **absolute URIs**.
Measured on a freshly written table:

    "location":      "file:///var/folders/…/channelflow/x"
    "manifest-list": "file:///var/folders/…/snap-….avro"

A tree copied elsewhere and restored there is unreadable: every pointer still
names where the table used to live. The metadata is not wrong, it is precise
about a place that no longer holds anything.

Two ways out.

**Rewrite the paths on restore.** The metadata JSON is easy. The Avro manifest
lists and manifests also carry absolute paths, and rewriting those means reading
and writing Iceberg's own metadata with its own schemas — which is the single
part of the format [[ADR-060]] adopted Iceberg in order to stop owning. Getting
it subtly wrong produces a table that reads until it doesn't, in the code path
that runs when everything else has already failed.

**Restore where it came from.** What every Iceberg deployment does. It costs the
capability above.

## Decision

**A backup restores to the location it was taken from.** The copy preserves each
file's path relative to the table's location, and a restore puts them back at
exactly the URIs the metadata names, then re-registers the table in the catalog.

[[REQ-WP-037]]'s acceptance is **narrowed, openly**: "a restore into a non-empty
target is refused" stays; "a restore can land anywhere" goes. The three tests
that asserted it are rewritten rather than deleted, because what they were
really checking — that a restore does not merge, that it reports where it
landed, that it refuses to land short — survives the change.

## Consequences

Losing a bucket's *contents* is still recoverable: recreate the bucket under the
same name and restore. What is no longer possible is restoring under a
**different** name — cloning production into staging, or moving a table between
prefixes. Those are migration operations rather than disaster recovery, and
nothing in this repository does them today.

This is a reduction in a guarantee that already existed, arrived at by
measurement rather than by preference, and it is recorded as a reduction so that
whoever needs the lost capability can find the reason and reverse the decision
rather than discover the limit during a recovery.

The alternative stays available: path rewriting is a later requirement, not a
closed door. If it is ever written, this ADR is superseded rather than worked
around.

**What did not change**: the copy order is still the writer's order — data
files, then the manifests naming them, then the manifest list, then the metadata
that names that. An interrupted backup still restores to its last complete
snapshot, for the same reason as before and with more layers to keep in order.
