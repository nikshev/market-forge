## Context

PRD §13A.28's Test D: "Production feature path fails validation if a transform
declares symmetric/centered future dependence."

The wording is unusual and worth reading closely. It does not say *detect*
centered transforms — it says the path fails when a transform **declares** one.
That is a design instruction: the transform is expected to say what it is, and
the engine is expected to act on the declaration.

The alternative — inferring centredness by inspection — is not achievable in
general. A centered moving average, a Savitzky-Golay filter with a symmetric
window, `scipy.signal.argrelextrema`, and a hand-written loop that peeks at
`series[i + 1]` are all the same defect and look nothing alike. A checker that
caught three of them would give false confidence about the fourth.

PRD §13A.6 makes the stakes concrete: "Centered/offline peak-finding may only
create labels and diagnostics, never live signals." Both kinds of transform are
legitimate and both will exist in this codebase — the research labels of
§13A.4 need centered windows by definition.

## Decision

**Every transform used by the turning-point engine declares `centered: bool`.**
The production path calls a guard that raises for any transform declaring
itself centered. Research and labelling paths call no such guard.

A source-level check runs alongside it, refusing the handful of library
functions whose whole purpose is centered smoothing or offline peak finding.

## Consequences

- **The declaration is a claim, and a wrong claim is not caught by this.** A
  transform that peeks forward while declaring `centered=False` passes. That is
  a real limit and the same class as the `@pytest.mark.trace` markers, which
  also assert something no tool verifies. Test A is the backstop: a transform
  lying about its causality will change an already-finalized output when future
  bars arrive, and future-bar invariance fails.
- **Two guards, not one, and they fail differently.** The declaration catches
  the honest case — someone reaching for a centered filter because it smooths
  better — at the call site, with a message saying why. The source check
  catches the import. Neither alone would be enough; the pair covers the
  realistic mistakes.
- **Research code is not hobbled.** §13A.4's symmetric `k`-neighbourhood labels
  are centered by definition and stay legal, because only the production path
  guards. The separation is the point: the PRD permits centered transforms and
  forbids them reaching live signals.
- **`centered` has no default.** A transform whose author did not consider the
  question cannot be constructed, which is the same reasoning [[ADR-015]]
  applied to the feature registry's fields.
