## Context

PRD §18.7.1 asks for "cumulative notional required for ±10/25/50/100 bps" from
the reconstructed tick map. On a real pool the map is incomplete: we know the
ticks whose `Mint`/`Burn` events we have seen, and a pool observed from a
mid-stream checkpoint has liquidity beyond them.

So a depth query can run out of known liquidity before reaching its target. The
tempting answers are all wrong:

- **Return the notional consumed so far**, which reads as "it costs this much
  to move the price 50 bps" when it actually cost that much to exhaust what we
  know about.
- **Extrapolate the last liquidity**, which invents a pool.
- **Return infinity**, which some consumer will plot.

All three produce a number, and a number is what a caller will act on.

## Decision

**A depth query that cannot reach its target returns a refusal** carrying the
distance actually reached and the notional consumed getting there — as data on
the refusal, not as the answer.

The same for a pool with no active liquidity: the price cannot be moved, and
that is not a cost of zero.

## Consequences

- **"This pool is too thin" becomes readable**, which is the useful finding. A
  quote that stopped at 30 bps when 50 was asked is a liquidity fact, and it is
  invisible if the return type is a number.
- **A consumer must handle the refusal**, which is the correct burden — PRD
  §18.9.1's executable-depth curve and §44A's DeFi context both need to know
  the difference between deep and unknown.
- **The partial figures are still available** on the refusal, so a caller who
  genuinely wants "how far can we get" can ask for it explicitly rather than
  receiving it by accident.
- **This is the same shape as [[ADR-026]]'s z-score** and REQ-WP-011's
  `normalized_delta`: a degenerate input produces no answer, never a plausible
  one.
