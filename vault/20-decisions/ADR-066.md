id: ADR-066
title: A null hashes as a length no payload can have
status: accepted
decides: [REQ-WP-053]
date: 2026-09-12

## Context

[[ADR-053]] made a dataset's identity a hash over canonically encoded rows. The
encoder length-prefixes each value after a per-type tag, so no separator can be
forged by a value that happens to contain one.

**It had no encoding for a null**, and `_encode` raised a `TypeError` for every
type's `None`. Nothing noticed, because every canonical table until now declared
its columns effectively non-null: `bars`, `signals`, `channels` and the rest fill
every field on every row.

PRD §18.12.1's `NormalizedSwap` does not. `notional_usd`, `sqrt_price_x96`,
`tick` and `liquidity` are absent on swaps nobody priced or on pools that report
no tick, and [[REQ-WP-053]] is the first table that has to store one.

**The storage side was worse than the hash side.** `_for_arrow` stringified
before checking, so a null decimal was written as the literal text `"None"`. It
read back as `Decimal("None")` and raised — the good direction — but the Parquet
file was already wrong, and PRD §6.4 plans for Trino and DuckDB reading those
files directly, where that text is what they would have seen.

## Decision

**Arrow stores a real null**, and the encoder marks one with a length of
`0xFFFFFFFF` — four gigabytes, against rows measured in bytes.

A length rather than a new tag, because the tag comes first and every non-null
value's bytes are then unchanged: **no content hash already recorded in the
registry moves.** Verified by 158 existing lakehouse and table tests passing
untouched.

The column's type tag is kept in front of the null marker. A null decimal and a
null string in the same position stay different rows: the value is absent, the
column's meaning is not.

## Consequences

**"Empty" and "absent" are different datasets**, which they were not going to be
under the obvious alternative. `_encode` returns no bytes for an empty string and
for an empty list, so marking a null with an empty payload would have hashed a
null string identically to `""`. A mutation testing exactly that survived the
first pass and is now caught.

**A missing column is still refused.** A row that omits a column is a producer
bug; a row that says `None` is a producer saying it does not know. The encoder
distinguishes them, and only the second is now representable.

**This does not make nulls cheap.** Every argument in this repository against a
column that is null on every row still stands — `dex_swaps` leaves five of
§18.12.1's fields out entirely rather than declaring them and filling them with
nothing. What changed is that a column which is *sometimes* absent can now say
so, which is the distinction the whole "absent is not zero" line of reasoning
depends on and which the plane could not previously express.
