## Context

[[ADR-064]] (2026-09-12) met the first disappearance: MinIO's images left Docker Hub, the project moved to
`quay.io/minio/*` at the same releases and wrote down that "this will happen again, to some image".

It did, one month later. By 2026-10-11 neither `quay.io/minio/minio:RELEASE.2025-09-07T16-13-09Z` nor
`quay.io/minio/mc:RELEASE.2025-08-13T08-35-41Z` can be pulled by an anonymous client: quay answers `Requires
authentication` for the repository and `docker manifest inspect` fails for the pinned tags and for `latest`.
Docker Hub's `minio/minio` still answers `object not found`. The vendor has no registry left that serves the
community images at all.

The cost was not hypothetical. CI has been red since 2026-10-03 at "Start the object store", so lint, type
check, the full test run, the front-end checks and the traceability gate -- everything the pre-commit hook
defers to CI -- ran nowhere for eight days. And a stranger who clones the repository cannot start the stack,
because the running containers hold the images only from an earlier pull.

## Decision

**1. Replace the registry choice of [[ADR-064]] with a community fork, pinned by tag and by digest.**
`docker.io/pgsty/minio:RELEASE.2026-08-04T00-00-00Z@sha256:b6bfe723...2372` (the index digest, which covers
amd64 and arm64). It is a fork of MinIO's last open-source code ("SILO"), served from Docker Hub with
versioned tags, and the only candidate that is a drop-in: the same `server /data` command, the same
environment variables, and `mc` inside the server image. Candidates rejected: `bitnamilegacy/minio` (frozen,
no future), a Chainguard build (`latest` only -- not a pin), `rustfs/rustfs` (a different server, a different
S3 behaviour to re-verify).

**2. One image for the server and for the bucket step.** The fork's image contains `mc`, so
`minio_init` runs the server image and the separate client image is dropped. One fewer thing that can vanish,
and `ci.yml` runs the identical string (a test fails if the two differ).

**3. Digest pinning, which ADR-064 declined, is right here.** ADR-064 was correct that a digest would not have
helped when the *repository* disappeared. A digest is the answer to a different risk -- a *third party's tag
being re-pushed* -- and that risk is new: the vendor's releases were immutable by policy; a fork's are
immutable by the maintainer's good behaviour. For the vendor's own images (postgres, redpanda, prometheus,
grafana) the argument of [[ADR-064]] stands unchanged and they stay tag-pinned.

**4. The release is the one that was tested, not the newest.** `RELEASE.2026-08-04T00-00-00Z`: the 12
object-store integration tests pass against it on throw-away ports, and started on a copy of the live data
directory it lists 1,492 objects and returns the first 1,000 byte-identical to what the running 2025 server
returns (evidence in the implementation outcome note).

**5. A check, run first.** `python -m tools.images` (`make images-resolvable`) enumerates every image the
compose file (all profiles), the Dockerfiles and the workflows name, skips what the repository builds itself,
asks each registry whether it still resolves, and exits 1 for one that does not, naming it and where it is
referenced. CI runs it before its first pull. A rate limit or an unreachable registry is reported as
*unknown* and does not fail the run: a check that cries wolf on a throttled day is switched off the second
time. It is not in the pre-commit hook, because that hook's contract is that it needs no network.

## Consequences

**Provenance changes, and that is a real cost.** The object store now runs code from a community maintainer,
not from the company that wrote it. What mitigates it: the tag and the index digest (a re-pushed tag is
refused); credentials that are development-only (`channelflow_dev_only`) and ports that bind to loopback by
default; the integration run and the data comparison above. What remains: the maintainer could stop
publishing, or the fork could diverge from MinIO's S3 behaviour in a way these tests do not exercise. For
anything holding real value this would need the review a vendor image gets; this repository's stack is a
development and demonstration stack and says so.

**The running stack is not touched.** The change edits files; it recreates no container, and the running
MinIO keeps serving its own data directory. Moving the live store onto the new image is a separate, deliberate
step (stop, swap, start on the same volume -- shown to read on a copy, not yet done on the original).

**The exit is the one that was always there.** Another S3-compatible server behind the same endpoint and
bucket name. The check is what will announce that the time has come: it names the image the day it stops
resolving, instead of an obscure `docker run` error halfway through a job.

**What the check cannot see.** A job's `services:` images are pulled by the runner before any step, so the
check covers them but cannot guard them; and "resolves" is not "still the same bytes" -- that is the digest's
job, and only the fork has one.
