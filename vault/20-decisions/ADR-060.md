## Context

[[ADR-002]] decided the canonical data plane in one sentence: "Parquet on
S3-compatible object storage **with Iceberg table semantics**". PRD §7 names
Apache Iceberg as the format for "normalized, feature and research-grade
datasets where snapshot isolation, schema evolution, partition evolution and
reproducibility matter", and §6.4.9 makes Tier B — full research history —
Iceberg's.

What was built is a hand-rolled table layer that *implements* those semantics:
one manifest per commit under a version-named key, discovery by listing, atomic
commit through `put_if_absent`, snapshot isolation, point-in-time reads,
content-addressed dataset identity. It is careful work and every one of those
properties is tested.

It is also an approximation, and [[REQ-WP-038]] found the first place the
approximation diverges from the thing it approximates in a way that matters.

`Table.append` writes `files=(*parent.files, file)`. Each manifest names every
file in the table's history, so **the newest snapshot references every data file
ever written.** The newest snapshot must survive any retention policy — a table
with no current state is not retained, it is deleted with extra steps —
therefore no data file is ever unreferenced, therefore expiring snapshots frees
nothing but small JSON.

Iceberg does not have this problem, because Iceberg does not do this. A snapshot
points at a *manifest list*; each manifest names the files one commit added; the
files a snapshot sees are the union along the chain. Expiring old snapshots
genuinely unreferences their data files, and `expire_snapshots` plus orphan
removal is precisely the operation PRD §45 calls "S3 cold retention".

So the choice is not "should we adopt Iceberg". [[ADR-002]] adopted it. The
choice is whether to keep approximating it.

## Decision

**Adopt Apache Iceberg as the canonical table format, via `pyiceberg`.**

The hand-rolled `lakehouse.Table` is replaced rather than kept beside it. Two
table implementations would reintroduce exactly what [[ADR-002]] refused when it
rejected developing against a filesystem: a second path that diverges from
production and is exercised by nobody until it matters.

Catalog: a SQL catalog, SQLite-backed for local runs and CI's fast gate, and
PostgreSQL-backed on the dev stack and beyond. The fast gate must keep working
with no services running (REQ-INFRA-002), and a file-backed catalog satisfies
that without a second code path — it is the same catalog implementation with a
different URL, which is the distinction [[ADR-002]] drew between a test double
and a second production path.

Storage stays MinIO/S3 through `pyiceberg`'s FileIO.

**What is kept on top of Iceberg**, because Iceberg does not provide it:
[[ADR-053]]'s content-addressed dataset identity. Iceberg's snapshot ids are
allocated, not derived, so two runs producing identical data produce different
ids; PRD §0 item 13's reproducibility claim and [[REQ-REPRO-001]]'s registry are
built on a hash of the rows. That hash continues to be computed here.

## Consequences

This invalidates work. [[REQ-STORE-001]]'s table layer, [[REQ-WP-037]]'s backup
and restore, `lakehouse/research.py`'s extraction, and 110 tests are written
against the hand-rolled format. The migration is staged under [[REQ-WP-039]]
rather than performed in one commit, and until it completes the repository holds
a format it has decided to leave.

Backup and restore in particular were built two commits ago and their central
argument survives intact: the copy order is the writer's order, inverted for
removal. Iceberg's metadata layout differs and the invariant does not.

The gain is not only retention. Trino and DuckDB read Iceberg, which PRD §6.4.5
and §7 both assume and which nothing today can do; schema and partition
evolution stop being future work this layer would have had to grow; and the
format's correctness is somebody else's tested problem rather than ours.

The cost is a real dependency with a real surface, and a period during which the
plane is half-migrated. Both are named in [[REQ-WP-039]] rather than discovered.

**What this does not change**: the plane stays append-only, point-in-time reads
stay the reason it exists, and no operation may destroy data except the one
[[ADR-059]] gave the capability to. Iceberg makes retention *possible*; the
rules about what retention may not touch are unchanged, and [[REQ-WP-038]]'s
spec still holds.
