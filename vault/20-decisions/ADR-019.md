## Context

PRD §28's endpoints serve bars, channel snapshots, features and signals. PRD
§29 defines where those live — Iceberg tables on object storage, Pinot for HOT
serving, PostgreSQL for metadata ([[ADR-002]]). None of it is built. Nothing in
this repository persists anything: bars are produced in memory by REQ-WP-005,
snapshots by REQ-WP-006, candidates by REQ-WP-007, and all of them vanish with
the process.

The API could wait for storage. It cannot: REQ-WP-009's chart depends on it,
and the deep link REQ-WP-008 already emits points at a page that cannot exist
until it does.

## Decision

**The API depends on a repository protocol, not on a database.** One protocol
per entity kind — bars, channel snapshots, features, signals — with an
in-memory implementation for now.

The durable implementation arrives with PRD §29 and replaces the in-memory one
without any endpoint changing.

## Consequences

- **The endpoint tests need no service.** They populate an in-memory repository
  and assert responses; the whole API suite stays in the fast gate, which
  matters because it is the suite that will grow fastest.
- **The port is where the point-in-time rule can be enforced once.** FR-017
  says no module may read data later than the instant requested; a protocol
  with an `as_of` parameter makes that a signature rather than a convention
  each endpoint remembers.
- **An in-memory API is not a deployable one, and should not be mistaken for
  one.** Restarting loses everything. That is acceptable while nothing else
  persists either, and it must not become permanent quietly — this ADR is the
  record that storage is owed, not optional.
- **This is the third time the same shape has been used** — [[ADR-012]] for the
  book's transport, [[ADR-018]] for the alerter's. The pattern is deliberate:
  the thing that touches the outside world is supplied, so the code that makes
  decisions can be tested without it.
- Reversible by construction; that is the point of a port.
