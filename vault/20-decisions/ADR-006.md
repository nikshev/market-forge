---
id: ADR-006
title: Decimal precision is set explicitly at import, not left at Python's default
status: accepted
decides: [REQ-WP-002, REQ-WP-005]
date: 2026-09-08
---

## Context

Python's default decimal context rounds every arithmetic result to 28
significant digits. That is a property of the context, not of the values, so it
applies to every multiplication and division in the codebase silently.

Found while implementing REQ-WP-005: a VWAP test using a price with 29
significant digits failed, and the loss turned out not to be in the division at
all. `price * quantity` had already rounded — including in
`connectors/binance/normalize.py`, which computes `notional_quote` the same way
and is part of REQ-WP-003, already merged.

REQ-WP-002's specification says monetary quantities are exact decimals and its
tests exercise 28-digit values. The guarantee was stated more broadly than the
default context holds it.

## Decision

`channelflow/__init__.py` sets the decimal context precision to **60
significant digits** at import, and a test asserts it stays set.

## Consequences

- **The stated guarantee and the actual behaviour now agree.** REQ-WP-002 claims
  exact monetary arithmetic; at 28 digits that was true for every realistic
  value and false for the values its own tests used. Either the claim or the
  context had to move, and narrowing the claim would have been the worse
  direction.
- **No practical value was ever at risk.** A BTC price near 78918.01 times a
  quantity near 0.00204 needs roughly ten significant digits. 28 was never
  binding on real data, which is why this survived a full requirement without
  being noticed — and why it is worth fixing before something depends on it.
- **Division still is not exact**, and cannot be. One third of a unit does not
  terminate in any precision. 60 digits reduces loss; it does not abolish it,
  and pretending otherwise would be the kind of overclaim this project keeps
  removing.
- **Setting a process-wide context is heavy-handed**, and deliberately so. The
  alternative — a `localcontext` at every arithmetic site — is exactly the kind
  of discipline that holds until someone adds a convenience method. An absence
  of local contexts is easier to verify than their presence everywhere.
- **It applies on import of `channelflow`.** Code that uses the domain models
  without importing the package would not get it; nothing does that today, and
  the test guards the property rather than the import order.
- Reversible: the number is one line. Lowering it later would be a decision
  about how much exactness costs, which is the right shape for that question.
