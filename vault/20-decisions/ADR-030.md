title: The external criterion is a separate split, and overlapping splits are refused

## Context

GMDH's defining mechanism is the *external* criterion: candidate nodes are
fitted on one subset and selected on another. Everything the method claims —
that it finds structure without overfitting, that layer growth terminates
honestly — rests on the selection data being unseen by the fit.

It is also the easiest thing to get wrong, and the failure is silent. A search
that scores nodes on their own training rows will grow layers as long as it is
allowed to, because each layer can always fit the sample better. Every
subsequent number — the comparison report, the interaction export, the
promotion gate — then describes a memorised sample.

This project already has the machinery: REQ-WP-017's folds are chronological,
purged and embargoed, which is a stronger guarantee than GMDH requires.

## Decision

1. **Fit and selection take separate splits, passed in explicitly.** There is
   no default that derives one from the other.
2. **Splits sharing any row are refused** at the start of the search, not
   detected later.
3. **A one-row validation split is refused**: a criterion computed on one row
   selects noise.
4. **The search consumes REQ-WP-017's folds directly**, so a caller using them
   gets purging and embargo for free.

## Consequences

- **The refusal is cheap and the alternative is undetectable.** Comparing two
  row sets costs nothing; a search that quietly selected on training data would
  produce a plausible model and a good-looking report, and nothing downstream
  would contradict it.
- **The caller must think about the split**, which is the correct burden. A
  helper that split the data itself would pick a rule — random, chronological,
  by fold — and that rule is exactly what PRD §41 rules 1 and 10 are about.
- **A test that fits perfectly on training and badly on validation must be
  pruned**, and that test is the specification of this ADR: it fails under any
  implementation that scores on the fit data.
- **This mirrors REQ-WP-017's own design**, where the leakage checker takes a
  protocol rather than the validated type. Both are the same instinct: make the
  guarantee checkable from outside the thing that claims it.
