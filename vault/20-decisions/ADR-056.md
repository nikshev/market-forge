title: A writer to an append-only plane is idempotent per series, or it is wrong
status: accepted

## Context

[[REQ-STORE-001]] built the canonical plane append-only on purpose: a snapshot
is immutable, so a dataset identity stays true and a point-in-time read cannot
be rewritten under a reader. Nothing in it rejects a row it already holds —
that is not an oversight, it is what append-only means.

[[REQ-PIPE-001]] put the first writer on it. Every one of its twelve tests
started from a fresh `InMemoryObjectStore`, so every one of them asked the same
question: does a run over an empty store write the right rows? All twelve said
yes, the mutation sweep caught eight of ten mutants, CI was green, and the
requirement reached `implemented`.

Then a second run over the same input:

    first wrote 2 | second wrote 2 | table holds 4

Two signals became four. Nothing raised, nothing logged, and every reader
downstream reported the four as fact: the API returns each signal twice, a
count of signals is double, and the dataset hash over the doubled table is a
perfectly valid identity for a dataset that is wrong. The requirement's own
Scope had even named this and dismissed it — "one replay, one batch per table"
— which is true within a run and false across runs, the distinction the
sentence did not make.

The suite could not have caught it. A fresh store per test is not a weak
fixture; it is a fixture that cannot express the question, because the second
run is the whole of the question.

## Decision

**Every pipeline entry point reads a per-series watermark before it writes, and
writes only past it.** Not "should"; one that does not have one is incorrect,
because append-only means the plane will not stop it.

The rule binds entry points that take a batch of recorded input and can be run
again over it — `record_bars`, `record_replay`, the live sink when it exists, a
backfill. It deliberately does **not** bind the single-item writers on
[[REQ-STORE-002]]'s repository (`add_bar`, `add_signal`, and the rest). Those
are literal primitives: the caller said append, so they append, and the
in-memory repository behaves identically, which is what keeps the two
implementations answering alike. Idempotence there belongs to whoever is
calling them in a loop — and that caller is a pipeline entry point, which this
rule binds.

Four things this requires, each of which was a way to get it wrong:

1. **Scoped to the series, not the table.** A watermark over the whole table
   would refuse a symbol's first bar on the strength of another symbol's
   hundredth — and the second symbol would simply never appear, with nothing
   raised.
2. **Absent, not zero, for a series never seen.** Zero is a real instant. A
   table reporting it for an empty series refuses every event at or before the
   epoch.
3. **Strictly past it.** The row *at* the watermark is the one already there.
4. **Skips counted, not silent.** A re-run is a no-op and should look like one.
   A number that stays at zero is a run that added something — the same reason
   `BarBuilder` counts its late trades rather than dropping them quietly.

**A recording names the tables its run is answerable for** — wrote to, or
skipped rows destined for — not the tables that happen to hold something. Those
are the same question only on a fresh store, which is the assumption this ADR
exists to retire. A run that skipped everything still names its dataset: what it
would have written is already there, so those snapshots are exactly the dataset
its input corresponds to, and re-running to recover a lost citation is worth
allowing.

## Consequences

- Both entry points are idempotent per series, and a resumed run over
  overlapping input writes only the tail that is new. Resumability was listed
  as out of scope in [[REQ-PIPE-001]]; it is in, and the note says so.
- A watermark is a full scan of the table per run today. That is honest for the
  row counts here and will not stay so; the plane's snapshots carry per-file
  bounds ([[REQ-STORE-001]]), and a watermark should eventually read them
  instead of the rows. Nothing depends on the current implementation beyond its
  answer.
- **Every future writer inherits this, including the live sink.** PRD §25.1's
  live mode attaches the same recorders. A live process restarted after a crash
  replays its overlap; without the watermark it doubles it.
- Tests over this plane start from a store that has already been written to,
  not a fresh one. A fresh-store test cannot fail this way, so a suite made
  only of them proves less than its green count suggests.

## Alternatives considered

- **Make the plane reject duplicates.** It cannot: the plane stores opaque rows
  and has no notion of a series or a key. Giving it one would make it a
  database, which [[ADR-002]] deliberately did not build.
- **Deduplicate on read.** Moves the cost to every reader forever and leaves the
  table wrong — and a dataset hash is taken over the table, not over a read.
- **Refuse a run whose input overlaps at all.** Simple, and it breaks the
  ordinary case: a feed resumed from an overlapping window would lose the tail
  that is genuinely new.
