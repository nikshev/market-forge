## Context

PRD §27.1's deep link carries `signal=<uuid>`, and dedupe needs a stable way to
say "this setup, again". `Candidate` has no id field: its identity is
`(venue, symbol, timeframe_ns, opened_at_ns)`.

A random UUID would satisfy the URL format and break two things. Principle XI
requires every result to be reproducible from a versioned dataset, config and
commit; Principle VII requires live and replay to be the same code. A replay
that produced different signal ids from identical input would produce different
alerts, different dedupe decisions and different audit records — all of them
looking correct.

## Decision

The signal id is a **deterministic digest of `(venue, symbol, timeframe_ns,
opened_at_ns, direction, boundary)`**, rendered as a UUID so §27.1's format
holds.

## Consequences

- **A replay of a recorded stream produces byte-identical alerts.** That is what
  makes an alert testable at all: `test_the_message_matches_expected_output`
  can compare against a literal.
- **Dedupe gets its key for free.** "The same setup" is the same id, which is
  the same tuple — not a heuristic over fields.
- **Two candidates cannot collide.** One machine holds one candidate per symbol
  and timeframe (REQ-WP-007 FR-014), and a candidate that has terminated cannot
  reopen on the same bar (FR-018), so `opened_at_ns` is unique within the tuple.
- **The id is not secret and does not need to be.** It identifies a public
  market setup; deriving it from its own attributes is a feature, since anyone
  holding the same data computes the same id.
- **A digest is not a random UUID and should not be mistaken for one.** It is
  version 5-shaped: reproducible by construction, with no entropy. Anything
  relying on unguessability must not use it.
