id: ADR-025
title: A leakage check that passes over no rows is a failure
status: accepted
decides: [REQ-WP-017]
date: 2026-09-08

## Context

Every check in this feature is of the form "no row violates X". Such a check
passes trivially over an empty dataset, and an empty dataset is the most likely
output of a broken build: a filter with an inverted condition, a horizon longer
than the data, a universe query that matched nothing.

The failure mode is specific and bad. A build that silently produces nothing,
followed by a leakage report that says everything is clean, reads exactly like
success. The next step — training a model — then fails for an unrelated-looking
reason, or worse, succeeds on a handful of rows that survived.

The same shape has appeared three times in this repository already:
REQ-WP-010's backtest fixture that produced no candidates, REQ-WP-011's
registry tests that would pass over an empty registry, and REQ-WP-019's Test A
comparing two empty lists.

## Decision

**A leakage check over an empty dataset fails**, with a message saying the
dataset is empty rather than clean.

Every "no row violates X" check is paired with the count of rows it examined,
reported alongside the result.

## Consequences

- **"Clean" now means something was checked.** The report says how many rows
  each rule examined, so a rule that silently applied to nothing is visible
  rather than indistinguishable from a rule that passed.
- **A legitimately empty build is inconvenient**, and that is the right trade.
  A dataset with no rows is not a dataset; the caller wanted rows and got none,
  and the loudest possible failure is the useful one.
- **This generalizes a habit into a rule.** The three earlier cases were each
  caught by a guard test written after the fact; making it a property of the
  checker means the next one is caught before anyone notices the pattern.
